# Web 代理性能记录

2026-10-13，Apple M4（10 核 CPU、32 GiB 内存）的 macOS / ARM64 本机上对比 `5ba7244` 与本次 Web 协议及模板实现。两者使用相同优化级别的 Rust release 构建；macOS 的 strip 均设为 `none`。这是本地回环测试，不代表 NAS、公网或有丢包网络的性能。

## 方法与结果

42 条域名规则，上游固定返回 1 KiB；并发 32，每种协议预热 1,000 次，随后执行 3 轮、每轮 200,000 次。HTTP/1.1 为明文，HTTP/2 与 HTTP/3 使用本地受信任证书。HTTP/3 客户端在一条 QUIC 连接中以 32 请求为批次，HTTP/1.1/2 客户端持续补充并发；**不能用这张表横向比较三种协议的优劣**。

| 场景 | 原版请求/秒 | 新版请求/秒 | 原版 P95 | 新版 P95 |
| --- | ---: | ---: | ---: | ---: |
| HTTP/1.1 | 59,305 | 66,283 | 0.871 ms | 0.712 ms |
| HTTP/2 | 43,998 | 49,919 | 1.012 ms | 0.912 ms |
| HTTP/3 | — | 30,618 | — | 0.961 ms |
| HTTP/1.1 + 4 条动态头 | — | 62,553 | — | 0.822 ms |

表中取三轮中位数，所有轮次失败数为 0。动态头为三个请求头变量和一个响应状态模板，相对同版未启用模板的 HTTP/1.1 吞吐低约 5.6%。这次对照未发现原有 HTTP/1.1/2 路径回退；结果仍受同机调度与系统负载影响，不承诺固定提升比例。

额外以并发 8 分别完成 HTTP/1.1 与 HTTP/3 的 16 次 16 MiB 下载，共各 256 MiB。两者均零失败；代理进程观测到的峰值 RSS 分别为 42.6 MiB、45.5 MiB，响应未整块缓存在代理内存。RSS 每 50 ms 采样，短暂分配可能未被捕获；这不是所有生产负载下的内存上限。

## 实现中的资源边界

- 域名与入口使用哈希路由，共享只读快照；上游地址、TLS 与 Header 模板在配置刷新时解析。
- 上游复用连接，每目标最多保留 64 条空闲连接，60 秒回收。
- 固定 Header 绕过模板执行；模板限制语法、指令数、深度和输出大小。
- HTTP/3 全局最多 64 连接、256 活跃请求；每连接 32 个双向流，接收/发送窗口及应用队列有界。
- 响应完成或客户端断开后取消无用的流工作；持续流式转发，保持背压。
- 访问采集使用有界队列；过载丢弃数可在管理台查看。

## 复现

先从需要对照的旧版本构建并保留 release 二进制，然后在当前工作区运行：

```sh
cargo build --release --locked --examples
cargo build --release --locked
python3 backend/tests/benchmark.py \
  --baseline /absolute/path/to/previous/openlucky \
  --requests 200000 --rounds 3
```

macOS 若遇到 proc-macro 的 LINKEDIT strip 错误，两份构建均加入 `CARGO_PROFILE_RELEASE_STRIP=none`。不要在同时编译或部署时进行对照测试。原始结果写入被 Git 忽略的 `.myself/qa/web-performance.json`；测试只启动临时数据和回环服务，不访问生产 DNS。

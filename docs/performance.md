# Web 代理性能记录

2026-10-13，Apple M4（10 核 CPU、32 GiB 内存）的 macOS / ARM64 本机上对比 `5ba7244` 与本次 Web 协议及模板实现。两者使用相同优化级别的 Rust release 构建；macOS 的 strip 均设为 `none`。这是本地回环测试，不代表 NAS、公网或有丢包网络的性能。

## 方法与结果

42 条域名规则，上游固定返回 1 KiB；并发 32，每种协议预热 1,000 次，随后执行 3 轮、每轮 200,000 次。HTTP/1.1 为明文，HTTP/2 与 HTTP/3 使用本地受信任证书。HTTP/3 客户端在一条 QUIC 连接中以 32 请求为批次，HTTP/1.1/2 客户端持续补充并发；**不能用这张表横向比较三种协议的优劣**。

| 场景 | 原版请求/秒 | 新版请求/秒 | 原版 P95 | 新版 P95 |
| --- | ---: | ---: | ---: | ---: |
| HTTP/1.1 | 59,305 | 66,283 | 0.871 ms | 0.712 ms |
| HTTP/2 | 43,998 | 49,919 | 1.012 ms | 0.912 ms |
| HTTP/3 | — | 30,618 | — | 0.961 ms |
| HTTP/1.1 + 4 条动态头 | — | 62,553 | — | 0.822 ms |

表中取三轮中位数，所有轮次失败数为 0。动态头为三个请求头变量和一个响应状态模板，相对同版未启用模板的 HTTP/1.1 吞吐低约 5.6%。这次对照未发现原有 HTTP/1.1/2 路径回退；结果仍受同机调度与系统负载影响，不承诺固定提升比例。

额外以并发 8 分别完成 HTTP/1.1 与 HTTP/3 的 16 次 16 MiB 下载，共各 256 MiB。两者均零失败；代理进程观测到的峰值 RSS 分别为 42.6 MiB、45.5 MiB，响应未整块缓存在代理内存。RSS 每 50 ms 采样，短暂分配可能未被捕获；这不是所有生产负载下的内存上限。

## 首轮压测时的资源边界

- 域名与入口使用哈希路由，共享只读快照；上游地址、TLS 与 Header 模板在配置刷新时解析。
- 上游复用连接，每目标最多保留 64 条空闲连接，60 秒回收。
- 固定 Header 绕过模板执行；模板限制语法、指令数、深度和输出大小。
- HTTP/3 全局最多 64 连接、256 活跃请求；每连接 32 个双向流，接收/发送窗口及应用队列有界。
- 响应完成或客户端断开后取消无用的流工作；持续流式转发，保持背压。
- 访问采集使用有界队列；过载丢弃数可在管理台查看。

## 复现

先从需要对照的旧版本构建并保留 release 二进制，然后在当前工作区运行：

```sh
cargo build --release --locked --examples
cargo build --release --locked
python3 backend/tests/benchmark.py \
  --baseline /absolute/path/to/previous/openlucky \
  --requests 200000 --rounds 3
```

macOS 若遇到 proc-macro 的 LINKEDIT strip 错误，两份构建均加入 `CARGO_PROFILE_RELEASE_STRIP=none`。不要在同时编译或部署时进行对照测试。原始结果写入被 Git 忽略的 `.myself/qa/web-performance.json`；测试只启动临时数据和回环服务，不访问生产 DNS。

## NAS 容量与采集优化对照（2026-10-13）

以提交 `ed41ba8` 的 release 构建为基线，比较本次窗口/日志优化；硬件仍为上述 M4。以下两组对照时上游空闲连接上限仍为 64；后续连接池修复与最终版本的 128 并发结果另列在后面。两版均开启相同 Web 功能，使用相同客户端；HTTP/3 客户端现在持续补充并发，只有首个响应计算内容校验摘要。因此本节不能直接与上面的旧 HTTP/3 数值比较。

每场景一轮 30 秒、32 并发、1 KiB 响应，所有请求成功。单轮结果用于检查回退，不代表统计上稳定的固定收益；尤其约 1–4% 的变化需要多轮复测。

| 场景 | 基线请求/秒 | 新版请求/秒 | 基线 P99 | 新版 P99 | 每请求 CPU 时间变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| HTTP/1.1 | 67,763 | 69,587 | 1.244 ms | 1.200 ms | 下降约 6.4% |
| HTTP/2 | 45,420 | 45,979 | 1.308 ms | 1.342 ms | 下降约 6.5% |
| HTTP/3 | 27,744 | 28,781 | 2.150 ms | 2.018 ms | 下降约 3.3% |
| HTTP/1.1 + 动态头 | 65,056 | 64,131 | 1.288 ms | 1.410 ms | 未采样 |

本轮动态头吞吐下降约 1.4%，不能据此宣称所有场景均有提升。基线报告 6,131,407 条队列溢出明细；新版主动略过 6,233,240 条成功明细，队列丢弃、统计桶丢弃和写入失败均为 0。两版采用的明细采集策略不同，吞吐对照包含这项策略变化；不代表新版能全量记录每一次访问。

另外通过 `quic_latency.py` 的有界 UDP 回环中继，为双向数据包各增加 25 ms 延迟；并发 8，在同一 QUIC 连接完成 16 次 16 MiB 下载，总计 256 MiB：

| HTTP/3 大文件，模拟 50 ms RTT | 基线 | 新版 |
| --- | ---: | ---: |
| 完成总耗时 | 32.397 s | 7.938 s |
| 有效载荷吞吐 | 66.29 Mbps | 270.53 Mbps |
| 请求失败 / 中继主动丢包 | 0 / 0 | 0 / 0 |

该场景吞吐约提升 4.08 倍，符合发送窗口从 512 KiB 增至 2 MiB 后解除在途数据限制的预期。中继自身的调度、UDP 栈、CPU 也影响结果；这不是 NAS、公网丢包或真实物理链路的吞吐保证。

后续 128 并发测试中，HTTP/2 转 HTTP/1.1 上游出现 29,540 次失败（88,635 次请求）。把同一配置的上游空闲连接上限从 64 增至 256 后，HTTP/2 场景恢复零失败、约 55,825 请求/秒；结果支持空闲池容量不足导致高并发复用退化的判断，尚未单独追踪每次 TCP 建连/关闭。此参数现可通过 `OPENLUCKY_UPSTREAM_IDLE_PER_HOST` 调整，仍保留 60 秒回收。

最终版在客户端 128 并发、每场景 10 秒下，HTTP/1.1、HTTP/2、HTTP/3、动态头及两种大文件下载均零失败（HTTP/3 仍受每连接 32 个活跃流限制，其余请求等待）。总计 2,341,745 次请求，持久化聚合计数精确相等；主动采样略过 2,333,529 条，存储 8,216 条，队列丢弃、统计桶丢弃、写入失败均为 0。代理观测峰值 RSS 最高约 50.2 MiB；这仍不是全部生产场景的内存上限。原始结果为 `.myself/qa/nas-concurrency128.json`。

复现命令（基线必须先在旧提交编译并另存）：

```sh
python3 backend/tests/benchmark.py --baseline /path/to/ed41ba8/openlucky \
  --baseline-http3 --duration 30 --rounds 1 --output .myself/qa/nas-performance.json
python3 backend/tests/benchmark.py --baseline /path/to/ed41ba8/openlucky \
  --baseline-http3 --large-only --quic-rtt-ms 50 --rounds 1 \
  --output .myself/qa/nas-quic-rtt50.json
```

持续模式每轮允许 1–120 秒，另设 1,000 万请求的客户端内存保护上限；以输出的实际 `seconds` 和 `requests` 为准。`--concurrency` 可测 1–256 并发。基准结束会等待落盘并断言聚合请求总数等于客户端实际发送数（包含预热）。HTTP/1/2 的 `proxy_load` JSON 还支持 `rate` 指定目标请求速率，延迟从计划发送时刻计算，包含等待并发槽的时间；失败请求耗时也计入分位数。HTTP/3 仍为固定并发模式，不把它当作固定到达速率测试。

NAS 上线后的容量验收仍需独立客户端与上游、真实网络延迟/丢包、TLS 新建连接以及更长时间负载，并同步记录 cgroup 节流、RSS、错误率和 P99/P99.9。默认 CPU/内存配额没有因本次优化而上调。

最终 `.myself/check.sh` 通过：22 项 Rust 测试、真实协议与重启测试、部署快照/回滚测试、前端构建及 7 项浏览器测试。生产 Dockerfile 的 Rust 1.89 / linux-amd64 镜像构建成功；在本机 Colima 用无网络、只读根目录、临时数据、1.5 核 / 384 MiB 启动后健康检查通过，并验证超预算配置拒绝启动。验证容器已删除；本次没有切换 NAS 上的生产容器。

## 服务分组查询（2026-10-14，本机调试构建）

`backend/tests/groups.py` 在隔离数据库中放入 42 个服务、每服务 720 小时，共 30,240 个小时桶，并连续请求 10 次 `/group-stats?hours=720`。本次中位数 39.2 ms、最大 39.6 ms，逐次核验请求合计和加权耗时。此数据用于管理查询回归，不代表 NAS 性能或生产吞吐。

分组摘要一次查询返回全部组，前端共享缓存并按 10 秒轮询；归组和排序不会新增代理请求路径中的数据库查询或锁。已有 HTTP/1.1、HTTP/2、HTTP/3、流式上传下载及升级协议继续经过完整回归。
